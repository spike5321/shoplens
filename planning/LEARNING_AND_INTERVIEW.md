# 学习路线、GitHub参考与面试准备

## 1. 为什么选择这个方向

已有 MockMate 用于讲自研工具调度、对话状态、检索和评分。ShopLens 用于讲框架编排、SQL、业务数据正确性及持久化。两个项目可以共享 Python/FastAPI/React，但核心问题与证据不同。

不需要为了“差异化”把语言、前端和全部基础设施都换掉。评测与错误处理也应继续保留，它们是通用工程习惯。

## 2. LangChain 到底学什么

近期岗位样本中，有招聘将 LangChain/LangGraph/LlamaIndex 经验列为加分项，同时要求能说明项目取舍、问题和验证。这支持学习框架，但不足以推断所有面试都会考它。[岗位原文](https://jobs.tiangong.edu.cn/correcruit/content/id/55660.html)

当前官方定位：LangChain 提供模型、工具、消息、Agent 等抽象；其 Agent 构建在 LangGraph 上。LangGraph 提供更底层的状态编排、持久化与人工介入能力，也可以独立使用。[LangChain](https://docs.langchain.com/oss/python/langchain/overview)、[LangGraph](https://docs.langchain.com/oss/python/langgraph/overview)

| 内容 | 到什么程度 | 用什么证明 |
|---|---|---|
| 模型与消息 | 理解消息角色、tool call/result配对、模型能力差异 | 跟读一次真实请求与返回，隐藏Key |
| 工具与结构化输出 | JSON Schema/Pydantic、参数校验、错误反馈 | 手工触发一次非法参数和校验失败 |
| 预构建 Agent | 能用create_agent写小例子，知道循环由谁执行 | 一个独立可运行学习样例 |
| State/Node/Edge | 能解释图状态、条件路由、终止与修复上限 | 手画主流程并定位对应节点 |
| interrupt/checkpoint | 理解暂停、继续、重放以及存储边界 | 重启后继续等待澄清任务 |
| 上下文 | 知道哪些指标/Schema/示例提供给模型 | 展示一条查询的上下文来源 |
| 可观测性 | 能根据节点事件区分解析、校验、执行失败 | 复盘一个真实失败案例 |

无需背全框架API。把“为什么这里用框架、框架替我做了什么、仍需自己保证什么”讲清楚。

MockMate README中“用框架学不到Agent到底在干什么”可以在未来整理时改得更准确：“为了理解工具调用循环，本项目选择自行实现；后续使用框架时可以对照这些机制。”当前任务不修改旧项目。

## 3. GitHub学习清单

参考核对日期：2026-09-24。仓库可能更新，学习时记录实际版本或commit；示例的依赖与当前API不一致时，以对应版本官方文档和实际运行结果为准。

| 参考 | 只重点学习什么 | 用在本项目哪里 |
|---|---|---|
| [langchain-ai/langchain-academy](https://github.com/langchain-ai/langchain-academy) | 基础图、状态、消息、持久化与人工介入的相关notebook | 第2周图编排；先读所需部分，不必完成所有模块 |
| [LangGraph官方SQL Agent教程](https://docs.langchain.com/oss/python/langgraph/sql-agent) | 将查询生成、检查、执行拆成有约束的步骤 | 查询流程骨架；自行补充指标规则与执行器 |
| [Canner/WrenAI](https://github.com/Canner/WrenAI) | Schema以外的指标定义、单位、关联与示例如何组织 | 小型指标字典与业务上下文 |
| [vanna-ai/vanna](https://github.com/vanna-ai/vanna) | 查数产品如何展示SQL、表格、图表及执行过程 | 可选界面/产品参考，不引入整套框架 |

WrenAI和Vanna是学习参考，不是首版依赖。大型项目不需要完整部署后才能学习；先定位一个模块、一个类型定义、一个对应测试，追踪输入输出。许可需要按实际复用文件检查，不能仅凭GitHub首页一个标签概括整个仓库。

学习每个模块时，完成一张记录卡：

```text
来源：仓库/文档链接、commit或版本、日期
问题：它解决什么具体问题？
输入/输出：调用者传什么，返回什么？
机制：关键步骤和约束是什么？
取舍：它为什么这样做，有什么局限？
本项目应用：采用了哪一个思想或代码片段？
个人修改：为什么需要改？
验证：哪条测试/实测说明修改有效？
许可与署名：实际复制代码是否保留要求的声明？
```

参考阅读建议总计6–10小时，分散到需要用的阶段。超过一天仍在“通读大型仓库”时，应缩小到具体问题。

## 4. 基础知识的学习顺序

1. SQL优先：SELECT/WHERE、JOIN、GROUP BY、COUNT DISTINCT、CTE、NULL、日期、主外键和索引。能自己写出五个核心指标查询。
2. 数据口径：粒度、事实事件、维度、退款时点、重复计数、比例基期。先手算，再写程序。
3. LangChain/LangGraph：按上表掌握核心机制，不先学多智能体。
4. 后端数据：SQLAlchemy、迁移、连接池、数据库角色、事务、持久化任务状态。
5. 前端和部署：复用熟悉的React/FastAPI模式；能理解HTTP请求、Cookie归属、轮询与错误状态。
6. 评测：独立真值、开发/冻结集、对照条件、失败分母和复现实验。

算法、数据结构、网络和操作系统仍要在求职准备中保留固定时间；项目不能替代岗位基础题准备。

## 5. 每阶段必须自己完成的小练习

- 数据阶段：手工增加一笔跨月退款，预测两个期间净收款的变化，再运行验证。
- 执行器阶段：构造一个SELECT开头但不该允许的查询，说明究竟由哪一层拦截。
- 图阶段：把一个字段名故意写错，查看修复节点何时运行、何时停止。
- 产品阶段：刷新页面和重启后端，解释为什么结果还在、运行中的任务为什么显示中断。
- 评测阶段：挑一个“SQL成功但答案错误”的样例，人工确认错误源头并修复。

## 6. 可以深入讨论的面试问题

1. 你的MockMate自行写循环，这个项目为什么使用LangGraph？它节省了哪些工作，又没有替你解决哪些问题？
2. LangChain与LangGraph有什么关系？为什么没有把每一步都做成自主Agent？
3. 实付、退款和期间净收款分别根据什么时间字段？跨期退款如何解释？
4. 为什么订单、明细和退款直接关联会重复计数？为什么SUM(DISTINCT amount)不是正确修复？
5. SQL能运行为什么仍可能错？你的参考答案如何获得？
6. 如何限制模型生成的SQL？AST校验和数据库权限各有什么局限？
7. 为什么要澄清？哪些默认值可以直接展示，哪些需要用户补充？
8. checkpoint如何恢复？一个中断节点重放时，哪些副作用可能重复？
9. 模型纠错为什么只允许一次？实际提升和额外延迟是多少？
10. 冻结评测集如何避免泄露？失败请求、错误拒绝是否计入指标？
11. 为什么首版不用向量数据库？多大规模、什么失败证据会促使你增加检索？
12. 借鉴了哪个开源模块？你做了什么改变，依据是什么？
