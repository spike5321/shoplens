# 客单价为什么多出了分组

2026-10-27；只使用固定种子的合成演示数据。

## 问题与证据

用户问“2026年9月客单价是多少？”。产品实际配置基准中，规划结果为 `average_order_value`、9月、`group_by=[]`，但 SQL 额外按日、渠道和类别分组。旧冻结题的空数据期间和“上周”也出现额外按日分组。三题均在一次修复后仍被 `plan_mismatch` 阻断，未将错误结果当答案展示。

这确认错误出现在 SQL 生成阶段。生成上下文同时包含计划所选分组和指标的全部可选 `dimensions`，可能造成混淆；这是由输入/输出证据提出的解释，不能声称知道模型内部原因。旧试跑中同一道9月题曾成功，说明模型行为本身存在波动。

## 改了什么

在 `backend/app/query_model.py` 的 `DeepSeekQueryModel.draft` 中：

1. 生成/修复 SQL 时，从指标副本中去掉可选 `dimensions` 列表，以 `plan.group_by` 表达唯一的所选分组。规划阶段仍接收完整指标字典；共享字典没有被修改。
2. 明确 `group_by=[]` 时只输出 `value`，不生成维度列、GROUP BY 或 ORDER BY。

没有修改 SQL 输出、放宽 AST 校验、替换数据库角色或变更指标公式。相较于把 SQL 生成改成确定性编译，本次是保留原流程的小范围输入修正，仍依赖模型遵守指令，仍需后续校验。

## 用简单例子理解

三笔订单实付100、200、300元，即使第一单拆成两行商品明细，总客单价仍是600÷3＝200元。

```sql
SELECT CAST(SUM(paid_cents) AS NUMERIC)
       / NULLIF(COUNT(DISTINCT order_id), 0) AS value
FROM analytics.sales_lines
WHERE paid_at >= CAST('2026-09-01T00:00:00+08:00' AS TIMESTAMPTZ)
  AND paid_at <  CAST('2026-10-01T00:00:00+08:00' AS TIMESTAMPTZ)
```

这里金额单位仍是分，展示时转换为元。`DISTINCT order_id` 防止把商品明细当成订单；没有 GROUP BY 表示整体统计；`NULLIF` 让零订单返回空值，而不是除零报错。客单价按订单，不是按顾客人数。
